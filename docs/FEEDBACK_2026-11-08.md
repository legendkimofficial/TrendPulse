# TrendPulse 프로토타입 검토 및 개선 제안

- 작성일: 2026-11-08
- 용도: 팀 및 Claude와 공유할 검토 기록, 후속 개선 작업의 입력 자료
- 검토 대상: 초기 기획안, 팀 논의 스크린샷, 발표 자료, 대시보드 이미지, 구현 코드, 테스트, 실험 코드와 저장된 결과
- 문서 성격: **v0.1 검토 당시의 기록**. 아래 진단과 수치는 당시 상태를 설명한다. 이후 v0.2에 반영한 내용과 현재 남은 한계는 [진행 상황 보고](../PROGRESS.md)를 참고한다.

## 1. 전체 평가와 유지할 방향

**감쇠 윈도우로 새로운 키워드를 발견하고, DGIM으로 선택한 키워드를 자세히 보는 구조는 타당하다.** 미리 정한 키워드 목록으로는 새로운 화제를 발견하기 어렵다는 팀 논의가 현재 설계에 잘 반영되어 있다.

현재 프로젝트는 교과 알고리즘, 실제 뉴스 데이터, 정확 기준 방식과의 비교, 대시보드, 설명 도구까지 연결되어 있다. 다음 개선에서 특히 중요한 것은 **핵심 수치의 해석, 실험의 공정성, 실제 화제를 발견했다는 증거**다.

유지하고 발전시킬 강점:

- 정확 기준 방식을 함께 구현하여 근사로 인한 손실을 비교할 수 있다.
- 순위 역전 등 실패 사례를 숨기지 않고 제시한다.
- DGIM이 항상 메모리를 절약하지는 않는다는 조건부 결과를 보여준다.
- HuffPost 편향, 과거 데이터 재생, 날짜만 있는 데이터 등의 해석 한계를 명시한다.
- 집계용 저장 공간과 관련 기사 조회용 인덱스를 구분하려는 설계가 있다.

## 2. 검증 범위와 결과를 읽는 방법

### 직접 실행하여 확인한 사항

- 기존 테스트 17개 통과: `py -m unittest discover -s tests -t . -v`
- 캐시된 기사 209,527건을 처음부터 끝까지 `TrendEngine`으로 재생
- 종료 시점의 추적 대상, 힙 항목, Python 집계 객체 크기 추가 진단
- 입력 설정의 경계 조건을 Flask 테스트 클라이언트로 점검
- 도구 호출 없는 응답과 가짜 인용을 넣는 Solar mock 진단
- 토큰화, 중복 및 빈 제목 등의 데이터 점검

### 검토했으나 이번에 전체 재실행하지 않은 사항

- E1~E3 수치는 기존 `experiments/results/results.json`과 `summary.md`를 검토했다.
- 전체 실험 스위트를 재실행해서 기존 수치를 재현한 것은 아니다.
- 실제 Solar API 호출 및 답변 품질은 확인하지 않았다. mock 진단은 검증 장치의 유무를 확인한 것이다.
- 화면 피드백은 제공된 대시보드 이미지, PDF 렌더링 이미지, HTML/JavaScript 검토에 근거한다. 실제 브라우저 상호작용 전체를 검증한 것은 아니다.

추가 진단은 Windows / Python 3.14 환경에서 수행했다. 실행 환경, 측정 시점, 측정 범위가 달라지면 메모리와 시간 수치도 달라질 수 있다.

## 3. 핵심 수치: 키워드 개수와 실제 메모리를 구분

### 확인된 문제

현재 발표의 약 93% 절약은 **저장 키워드 개수의 평균 감소율**이다. 실제 Python 메모리 감소율과는 다르다.

실제 메모리에는 딕셔너리, 문자열, float, 최소 힙, 갱신 후 남은 힙 항목 등의 비용이 들어간다. 특히 제거 방식은 정확 기준 방식에 없는 힙을 사용한다.

전체 재생 종료 시점의 추가 진단:

| 측정 대상 | 제거 방식 | 정확 기준 방식 |
|---|---:|---:|
| 저장 키워드 수 | 3,507개 | 54,979개 |
| Python 집계 객체 크기 추정 | 2,157,551 bytes | 5,907,030 bytes |
| 해당 시점 감소율 | 키워드 수 93.6% 감소 | 객체 크기 비교 시 63.5% 감소 |

제거 방식의 힙 항목은 이 시점에 13,036개였다. 객체 크기는 `sys.getsizeof`를 재귀적으로 적용하여 중복 참조를 한 번만 세었고, 집계 객체의 딕셔너리와 힙 등을 포함했다.

이 표는 **종료 시점 한 번의 집계 객체 크기 추정**이다. 전체 앱의 RSS도, 기존 실험의 시간 평균 메모리도 아니다. 기존 92.9% 평균 키워드 수 감소율을 대체하는 최종 메모리 실험 결과로 사용하면 안 된다.

### 개선 제안

- 현재 지표 이름은 **저장 키워드 수 평균 92.9% 감소**로 표현한다.
- 실제 메모리는 동일한 시점과 조건에서 별도로 측정한다.
- 논리적 저장량, Python 자료구조 크기, 전체 앱 메모리를 구분한다.
- 비교용 정확 집계, 원문 데이터, 관련 기사 인덱스, 이력 저장 공간도 범위를 밝혀 보고한다.
- 전체 기사 목록과 인덱스가 메모리에 남아 있으므로, 집계 알고리즘의 절약 효과와 서비스 전체의 메모리 사용량을 각각 설명한다.

DGIM bit 수도 **압축 저장을 가정한 논리적 모델**이다. 현재 구현은 Python 정수와 리스트를 쓰고 절대 타임스탬프를 보관한다. 정확 구간 집계의 `min(등장 위치 저장 비용, N비트)` 역시 실제로 deque와 비트맵 사이를 전환하는 구현은 아니다. 양쪽 모두 이론적 저장량과 실제 구현 메모리를 구분해야 한다.

관련 파일:

- [decaying.py](../trendpulse/decaying.py): `_heap`, `memory_bytes_estimate()`
- [dgim.py](../trendpulse/dgim.py): `memory_bits()`
- [sliding.py](../trendpulse/sliding.py): `memory_bits()`
- [engine.py](../trendpulse/engine.py): `metrics()`, 전체 기사 및 인덱스 보관

## 4. 정확도: 기준 순위 재현과 화제 발견의 유용성을 구분

### 현재 수치의 정확한 의미

Top 20 99.93% 일치는 **정확 기준 방식과 Top 20 구성원이 얼마나 겹치는지**를 뜻한다. 사람이 중요하다고 판단한 화제를 맞힌 비율은 별도로 평가해야 한다.

기본 설정의 저장된 결과는 함께 제시하는 것이 좋다.

> 정확 기준과 Top 20 구성원이 평균 99.93% 겹쳤으며, 20개 전체의 순서까지 같은 시점은 89.7%였다.

전체 평균만으로는 일부 시점의 실패가 가려질 수 있으므로 최저 일치율, 시기별 결과, 대표 실패 사례도 제시한다.

### 유용성 평가 제안

1. 서로 다른 시기의 사건 약 10개를 선정한다.
2. 사건별 관련 키워드와 관찰 기간, 탐지 성공 기준을 먼저 정의한다.
3. 최초 등장, 기준 Top K 진입, 근사 Top K 진입 시점을 비교한다.
4. 키워드가 사건을 이해할 수 있는 표현인지 팀원이 평가한다.
5. 대표 기사와 설명이 실제 사건을 뒷받침하는지 평가한다.

Scalia 사례는 출발점으로 적절하다. 여러 사건으로 넓혀서 다음 두 질문에 각각 답할 수 있게 한다.

- 근사 알고리즘이 정확 기준의 순위를 잘 재현하는가?
- 사용자가 새로운 화제를 발견하는 데 도움이 되는가?

관련 파일: [실험 결과 요약](../experiments/results/summary.md), [실험 원본 결과](../experiments/results/results.json)

## 5. 처리 성능: 비교 작업 범위를 맞춘 후 재측정

### 코드에서 확인된 비교 조건 차이

| 실험 | 현재 측정 범위 차이 | 영향 |
|---|---|---|
| E1 | 정확 기준 방식에 최근 구간 고유 단어 수를 관리하는 `Counter`·deque 작업이 추가됨. 제거 방식에는 같은 작업이 없음 | 순수 집계 갱신 속도의 공정한 비교가 어려움 |
| E3 | 정확 방식에는 평가 시점의 조회 작업이 시간에 포함됨. DGIM은 평가 작업 대부분을 시간에서 제외함 | 처리 속도 수치의 작업 범위가 다름 |
| 순위 조회 | 현재 `top_k()`는 저장된 키워드를 대상으로 탐색함 | 입력 갱신 속도만으로 화면·순위 처리 성능을 설명하기 어려움 |

### 개선 제안

- 입력 갱신, 순위 조회, 엔진 처리, API 응답 시간을 분리한다.
- 입력과 측정 포함 작업을 동일하게 맞춘다.
- 여러 번 실행한 중앙값과 변동 범위를 보고한다.
- 순위 갱신 주기를 함께 명시한다.
- 현재의 ‘항상 더 빠르지는 않다’는 관찰은 유지하되, 구체적인 속도 배수는 재측정 후 확정한다.

지연 감쇠의 전역 계수 갱신은 O(1)이지만 기사 전체 처리에는 토큰별 갱신, 힙 관리, 주기적 재정규화·정리 등이 포함된다. 발표의 ‘O(1) 갱신’은 적용 범위를 명시하면 좋다.

관련 파일: [run_experiments.py](../experiments/run_experiments.py)의 `run_baseline()`, `run_pruned()`, `e3()` 및 [decaying.py](../trendpulse/decaying.py)의 `top_k()`

## 6. DGIM 추정 방식 결과의 해석

현재 midpoint와 textbook 추정식은 버킷이 비어 있지 않으면 항상 0.5 차이가 난다. 따라서 작은 등장 횟수에서는 상대오차 차이가 크게 보일 수 있다.

저장된 N=1,000, r=2 결과:

| 지표 | midpoint | textbook |
|---|---:|---:|
| 전체 평균 상대오차 | 7.9% | 26.8% |
| 등장 횟수 10회 이상 평균 상대오차 | 11.0% | 11.2% |
| Top 10 구성원 일치율 | 86.3% | 86.3% |

발표에서는 **작은 등장 횟수에서의 개선이 전체 평균에 크게 반영되었다**고 설명하면 정확하다. 전체 평균 개선이 순위 품질 개선으로 그대로 이어졌다고 해석하지 않도록 한다.

관련 파일: [dgim.py](../trendpulse/dgim.py)의 `estimate()`, [실험 결과 요약](../experiments/results/summary.md)

## 7. 신규 진입: 이벤트 정의와 지연 평가 보완

### 확인된 문제

- 현재 이벤트 대응은 같은 키워드에 대해 기준 시점 앞뒤 최대 2,000건 범위의 이벤트를 연결한다.
- 지연은 부호가 있는 `(근사 시점 - 기준 시점)`의 평균이다.
- 따라서 조기 탐지와 늦은 탐지가 상쇄될 수 있다.
- 표에서 평균을 정수로 반올림하므로 작은 평균 차이가 0으로 표시된다.
- 기본 실험은 100건 간격이므로 더 짧은 지연을 구분할 수 없다.

예를 들어 θ=0.5의 저장된 평균 시점 차이는 약 0.30건, 최대는 200건이다. 평균을 0건으로 표시하는 것만으로 모든 이벤트에 지연이 없다고 결론 내릴 수 없다.

### 개선 제안

- 이벤트 정밀도와 재현율을 함께 보고한다.
- 허용 대응 시간 범위를 명시하고 그 선택 이유를 설명한다.
- 조기 탐지 비율과 지연 탐지 비율을 분리한다.
- 절대 시점 오차의 중앙값·95백분위수를 보고한다.
- 늦게 탐지한 이벤트만의 지연 분포도 제시한다.
- 대표 사건 구간은 기사 한 건 단위로 정밀하게 평가한다.

### 화면 용어 정리

순위표의 `NEW`는 직전 화면 대비 진입이고, 오른쪽 신규 진입 피드는 일정 기간 Top K에 없었던 키워드의 진입이다. 사용자에게 서로 다른 의미가 같은 표현으로 보일 수 있다.

‘직전 대비 진입’, ‘첫 관측 진입’, ‘재진입’의 이름과 조건을 맞추고, ‘처음’이 전체 데이터 기준인지 현재 재생·관측 범위 기준인지 명시한다.

관련 파일:

- [run_experiments.py](../experiments/run_experiments.py): `new_entry_events()`, `compare()`
- [engine.py](../trendpulse/engine.py): `_take_snapshot()`
- [app.js](../web/static/app.js): `deltaCell()`, `renderEvents()`

## 8. 장시간 재생: DGIM 추적 한도와 수명 관리

### 전체 재생으로 확인된 문제

처음부터 전체 데이터를 재생하면 자동 추적 대상이 300개에 도달한 후 교체되지 않는다.

종료 시점에는 현재 Top 20 중 14개가 자동 추적되지 않았다.

`trump`, `biden`, `covid`, `russian`, `police`, `court`, `jan`, `abortion`, `dead`, `tweets`, `russia`, `twitter`, `texas`, `funniest`

따라서 현재의 ‘Top K 진입 시 자동 추적’ 설명은 장시간 동작에서 유지되지 않는다. 수동 `track()`에는 자동 추적과 동일한 한도 처리가 없다.

### 개선 제안

- 현재 Top K와 사용자가 고정한 키워드를 우선 유지한다.
- 오래 비활성 상태인 자동 추적 대상을 제거·교체하는 정책을 만든다.
- 자동·수동 추적에 일관된 자원 제한을 적용한다.
- 제거·재추적 시 관측 시작 시점이 바뀌었다는 사실을 표시한다.
- 모든 추적기의 만료 처리를 같은 기준 시점에서 수행한 후 메모리 지표를 계산한다.

추가 진단에서는 모든 추적기에 대해 `dgim_info()`를 호출하기 전후 총 버킷 수가 718개에서 469개로 바뀌었다. 조회되지 않는 추적기의 만료 항목이 메모리 지표에 남을 수 있다는 점을 점검할 필요가 있다.

### 발견 직후 집계가 작은 문제

현재 DGIM은 추적 이전 기사를 세지 않는다. 높은 감쇠 점수 옆에 DGIM 2건 등이 표시되면 사용자가 혼동할 수 있다.

값 바로 옆에 **관측 50/1,000건 · 관측 구간 집계 중**을 표시하는 방식을 권한다. 추적 시작 이전을 집계하지 않는 설계를 유지할지, 별도 초기화 기능을 추가할지는 명시적으로 결정해야 한다.

관련 파일: [engine.py](../trendpulse/engine.py)의 `_take_snapshot()`, `track()`, `dgim_info()`, `metrics()`

## 9. 시간과 ‘최근’의 의미를 명확하게 설명

`c=0.001`에서 `1/c≈1,000건`은 감쇠의 대표 규모다. 최근 1,000건 이전의 정보가 완전히 사라지는 창은 아니다.

- 반감기: `log(0.5) / log(1-c)` ≈ 693건
- 충분히 긴 스트림에서 최근 1,000건이 차지하는 가중치 합의 비율: `1-(1-c)^1000` ≈ 63.2%

설정에는 감쇠 상수와 함께 **약 693개 기사마다 영향 절반** 같은 설명을 제공하면 이해하기 쉽다.

2018년 이후에는 기사 밀도가 크게 줄어든다. 동일한 1,000건 창이 가리키는 날짜 범위가 달라지므로, 기사 수 기준 창과 날짜 기준 감쇠가 어떤 결과를 만드는지 비교할 가치가 있다.

또한 감쇠 상수 실험의 ‘순위 안정성’은 현재 **정확 기준과 근사 결과의 순서 일치율**을 측정한 것이다. 시간에 따른 순위 안정성은 연속 시점 순위의 변화 등 별도 지표로 측정해야 한다.

관련 파일: [engine.py](../trendpulse/engine.py)의 `clock()`, `_span_days()`, [PROGRESS.md](../PROGRESS.md)의 E2 해석

### 실제 토큰화에서 확인된 예

### 데이터 추가 진단

- 기사 수: 209,527건
- 같은 날짜·제목 조합 기준 중복 초과 건수: 426건
- 동일 링크 기준 중복 초과 건수: 41건
- 빈 제목: 6건

중복 초과 건수는 전체 건수에서 해당 기준의 고유 조합 수를 뺀 값이다. 같은 제목이라고 반드시 동일 기사인 것은 아니므로 중복 제거 기준을 먼저 정해야 한다.

### 개선 제안

- 단어 방식과 바이그램·개체명 방식을 비교한다.
- 약어, 인명, 기관명, 지명 처리 원칙을 명시한다.
- 전처리 변경 전후 순위 품질과 메모리 비용을 함께 측정한다.
- 불용어 목록과 중복 처리 규칙을 기록한다.
- 같은 날짜 안의 기사 순서를 여러 번 섞어 순위·신규 진입 시점의 민감도를 평가한다.

관련 파일: [text.py](../trendpulse/text.py), [data.py](../trendpulse/data.py)

## 11. Solar: 근거 기반 답변을 코드로 검증

### mock으로 확인된 문제

프롬프트는 도구 사용을 요구하지만 실제 요청은 `tool_choice="auto"`이며, 도구 호출 없이 반환된 답변도 그대로 수용한다. 인용된 기사 ID가 실제 조회 결과에 있는지 검사하는 절차도 없다.

추가 진단에서 도구 호출과 근거 없이 `근거 없이 쓴 답변 [#999999999]`를 반환하는 mock 응답을 넣었을 때도 `trace=[]`인 정상 Solar 모드 답변으로 수용되었다.

이는 실제 Solar 모델의 환각 빈도에 대한 실험이 아니다. **도구 사용과 인용의 적절성을 검증하는 애플리케이션 장치가 없다는 진단**이다.

### 개선 제안

- 통계와 기사 조회가 필요한 질문에서 필수 근거를 확보한 뒤 답변을 생성한다.
- 인용된 기사 ID가 실제 도구 조회 결과에 포함되는지 검사한다.
- 유효하지 않은 인용이나 근거가 부족한 답변은 재생성·제한한다.
- 기사 ID를 누르면 해당 근거가 열리도록 연결한다.
- 근거가 없는 질문과 아직 관측되지 않은 키워드에 대한 응답도 평가한다.
- 실제 API 키로 설정된 모델과 도구 호출 흐름을 검증한다.

Upstage 공식 API에서 `auto`는 도구를 사용하지 않는 답변도 허용하고, `required`는 도구 호출을 요구한다. 호출 여부 외에 필요한 통계·기사 근거를 확보했는지는 애플리케이션에서 별도로 확인해야 한다.

공식 자료: [Upstage Chat API](https://console.upstage.ai/api/chat)

### 서버 동시성

현재 `/api/ask`는 Solar 요청 동안 전역 잠금을 유지한다. 외부 API가 느리면 다른 상태 조회·재생 요청도 기다릴 수 있다.

필요한 엔진 상태를 일관된 스냅샷으로 복사한 뒤 잠금을 해제하고 외부 요청을 수행하는 구조를 검토한다. 답변에는 기준 시점을 표시하면 좋다.

관련 파일: [agent.py](../trendpulse/agent.py)의 `_solar_answer()`, [app.py](../app.py)의 `ask_agent()`

## 12. 입력 검증과 테스트 보완

### 재현된 문제

- `/api/reset`에 `snapshot_every=0`을 보내면 200 응답으로 수용된다.
- 이후 `/api/step`에 `n=1`을 보내면 0으로 나누기 때문에 500 오류가 발생한다.
- 음수 `warmup_factor`도 수용되므로 설정 검증 범위를 보완할 필요가 있다.

### 우선 추가할 의미 있는 테스트

- 잘못된 설정은 엔진 상태를 변경하기 전에 400 오류로 거부한다.
- 추적 한도에 도달한 후에도 새 Top K 키워드의 추적 정책이 동작한다.
- 수동·자동 추적의 자원 제한이 일관된다.
- 도구 호출 없는 답변과 유효하지 않은 인용을 검출한다.
- 초기화·재생·키워드 조회를 연결한 엔진/API 동작을 검증한다.

관련 파일: [engine.py](../trendpulse/engine.py)의 `EngineConfig.validate()`, [app.py](../app.py)의 `reset()`, [tests](../tests/)

- 실제 Solar와 오프라인 요약 모드를 명확히 구분한다.

발표의 중심 문장 제안:

## 14. 확장 기능 후보

### 급상승 탐지

항상 많이 나오는 단어와 새롭게 증가한 단어를 구분한다. 짧은 감쇠와 긴 감쇠 점수를 비교하되 서로 다른 창 규모를 정규화하고 최소 등장 횟수를 함께 적용해야 한다. 희귀 단어 한 번의 등장만으로 급상승 비율이 커지는 상황을 막는다.

### 순위 불확실성 표시

현재 점수의 과소추정 상한을 활용하여 점수 차이가 작은 키워드에 **근사 오차로 순서가 바뀔 수 있음**을 표시한다.

교과의 오차 보장을 사용자가 이해할 수 있는 기능으로 연결할 수 있다는 장점이 있다. 실제 순위 보장 조건과 표시 문구는 구현 전에 검증한다.

## 16. Claude에게 전달할 작업 맥락

이 문서는 프로토타입에 대한 리뷰이며 제안 전체를 한 번에 구현하라는 확정 요구사항은 아니다. 실제 수정 범위는 사용자와 합의한 작업을 따른다.

후속 작업에서는 다음을 지켜 결과를 추적할 수 있게 하면 좋다.

1. 확인된 버그, 실험 해석 변경, 선택적인 기능 확장을 구분한다.
2. 실험 조건이 바뀌면 기존 결과를 새 조건의 결과로 혼용하지 않는다.
3. 실험 코드를 수정한 뒤 결과와 발표 수치를 함께 갱신한다.
4. 수치에는 데이터 범위, 준비 구간, 평가 간격, 실행 환경, 메모리 측정 범위를 기록한다.
5. 실제 API를 사용하지 않았다면 mock 통과와 실연동 검증을 구분한다.
6. 구현 후에는 변경 이유, 검증 결과, 남은 한계를 정리한다.
